# Development releases, upgrades, and recovery

The package remains `0.1.0` during local milestone development. Stage numbers describe scope, not semantic package versions. A future reviewed release should increment the development minor version when it introduces schema changes or material features, and patch versions for compatible fixes. Keep `package.json`, npm lockfile, Cargo manifest/lockfile, Tauri configuration, and installer-verification tooling consistent in that separate release change. Do not imply that equal development package versions guarantee equal database compatibility. Record the source commit and package hashes.

Before an owner-authorized upgrade of a normal profile, export the current complete records to a private off-device location, retain the prior installer/source identity, and confirm recovery can read that export. Close the app before installing. Check migration support, available storage, and release notes. Use coherent snapshots or complete exports; SQLite can retain committed WAL data even after a process exits, so moving only its main file can separate it from required journal data. Stage 4.5 testing uses unique application identifiers and disposable repository-local profiles; it does not upgrade the normal installation.

Release notes must identify supported database/interchange versions, migration direction, recovered history, changed authority or protocol definitions (if any), verification evidence, and known limitations. This unsigned Windows installer can show an operating-system warning and requires preinstalled Microsoft Edge WebView2. There is no updater or automatic release installation.

Database migration is forward-only. An older app rejects a newer schema; replacing its executable does not downgrade its data. To return to an earlier app, preserve the newer profile and use a separately isolated profile with a compatible earlier export or pre-migration backup. Work created after that recovery point is not represented in it. Never silently discard newer history or reuse lost reward entitlements through a downgrade.

The recovery panel lists the latest verified automatic snapshot date. Preview is read-only; **Replace local records** requires explicit confirmation and saves displaced readable state first. When the primary cannot open, **Export recovery copy** still exports the latest supported, validated automatic snapshot through a native Save dialog, without replacing the corrupt primary. An existing empty or uninitialized primary also fails visibly instead of silently becoming a new workspace. The error and recovery controls remain available after export. Preserve the entire failed profile, including any WAL/SHM files, for diagnosis; then import the complete recovery JSON in an explicitly chosen fresh private installation/profile. If no verified automatic snapshot is available, use a prior complete portable export. Do not rename/delete a normal profile casually. A future support/release procedure must identify the exact intended profile before any manual change.

Daily snapshots use the private backup directory. Retention is bounded only for verified subsystem-owned daily snapshots: newest seven dates plus newest point in each of three newest represented months. Migration, pre-restore, unknown, and unverified files are kept. A daily point reflects the first successful changed-data protection that day, not necessarily the day's last edit. Export records when a more recent or off-device point is needed. Backup contents may contain private work/evidence; never attach them to public issues.

Archiving and hiding are organizational, and corrections are append-only factual amendments. Neither is erasure. Full user-requested erasure requires a separately reviewed namespace-reset/tombstone policy so deletion cannot silently reopen reward budgets or break references. No reset shortcut is provided here.

## Separate CI proposal

No workflow is added in Stage 4.5. A separately authorized PR can use ordinary `pull_request` triggers, read-only contents permission, no secrets, no release/write permission, and no privileged `pull_request_target` execution. It should run pinned npm install/tests/typecheck/build, Rust formatting/tests/strict Clippy, and explicit concurrency cancellation. Review cache poisoning/fork boundaries, a bounded one-job Rust build, artifact contents and short retention, runner minutes/storage costs, and Windows packaging scope before enabling it. Never upload profiles, work exports, or recovery databases as CI artifacts.
